## Residual Review Findings

Validated by an independent reviewer, not applied because each needs a design decision:

- **P2** `src/domain/migrate.ts:45` — Future-dated imported timestamps pin targets and defeat manual overrides (reviewer: security, confidence 75)
  - Why: Import accepts any finite timestamp, and target calculation trusts timestamps for ordering. Take a crafted completed session with `finishedAt: 8e15` (about year 275,000) and a recommendation of 500 kg for db-row. It stays the "latest" session forever: every workout finished afterward sorts below it. A manual target the user sets also loses, because `override.createdAt >= session.finishedAt` can never be true. The editor accepts the change, but the next workout still prescribes 500 kg. In the same way, a template with a future `updatedAt` beats every later legitimate backup, and an override with a future `createdAt` always stays the newest. In History the session shows a normal-looking start date, so the cause is hard to find. Rejecting timestamps later than the import time closes this.
  - Suggested fix: Pass `now` into parseBackup from previewImport. Throw BackupError('This backup has dates in the future.') when any value is negative or exceeds `now + 24h`: session startedAt/finishedAt/updatedAt/createdAt, override createdAt/updatedAt, or template/settings updatedAt. The 24-hour allowance is an assumption that covers clock skew between devices. Keep the check in backup.ts so the domain validators stay clock-free.

- **P2** `src/domain/prescription.ts:121` — Manual targets skip rep-range normalization after scheme edits (reviewer: correctness, confidence 75)
  - Why: Say the user sets a manual target (target editor on Home, Summary, or Settings, or the bodyweight 'choose resistance' control) and then changes that exercise's rep range. The next workout still prescribes reps from the old range, e.g. 18 kg 5/6/6 on a new 8-12 ladder, and the ladder then climbs one rep at a time from below the new minimum. The cause is that deriveCurrentPrescriptions only passes `producedUnder` for targets that come from a recommendation, so for an override normalizePrescription can see a set-count change but never a range change. That breaks KTD5 and the U3 scenario ('changing its rep range from 5-6 to 8-12 normalizes 18 kg 5/6/6 to 18 kg 8/8/8'). It also breaks the ExerciseEditor's own hint, 'Changing sets or reps restarts at the bottom at the same weight'. The fix is to record the range an override was created under and compare it, the same way recommendations already use the session's scheme snapshot.
  - Suggested fix: Record the rep range on overrides at creation: add an optional `scheme?: { minReps: number; maxReps: number }` to PrescriptionOverride and fill it in createOverride from the template exercise. Let normalizePrescription take a produced-under range, and in deriveCurrentPrescriptions pass `override.scheme` for override-sourced reps targets, so a changed min/max resets to bottomRung(sets, minReps) at the same load. Treat overrides without a stored range as unchanged, so off-ladder custom targets like 4/4/4 still work. Add a prescription.test.ts case: override, then rep-range change, gives the bottom rung.

- **P2** `src/features/settings/exportFile.ts:12` — Double-tapped backup can trigger a stray silent download (reviewer: julik-frontend-races, confidence 75)
  - Why: Tapping 'Back up now' twice before React paints the disabled state (SummaryScreen.tsx:129 and DataSettings.tsx:84 both gate only on local useState, not a store-level flag) starts two overlapping backUpNow() calls. The Web Share API spec rejects a second concurrent navigator.share() call with InvalidStateError while the first is still pending, but shareOrDownloadJson's catch only special-cases AbortError (exportFile.ts:16-19), so the second call falls through to downloadJson(...) -- silently dropping a backup file into Downloads at the same moment the user is looking at the native share sheet from the first tap, and calling recordBackup twice.
  - Suggested fix: Guard backUpNow with a module-level in-flight promise (let inFlight: Promise<...> | null = null; export function backUpNow(now = Date.now()) { return inFlight ??= run(now).finally(() => { inFlight = null }) }), so a second call while one is pending awaits the same share/download instead of starting a fresh navigator.share().


### Not validated (over the validator budget)

These survived the confidence gate but were over the review's 15-validator budget, so no independent check ran. Treat them as leads to confirm, not as confirmed defects.

- **P2** `src/data/backup.ts:83` — parseBackup's malformed-template and migration-failure error paths are untested (reviewer: testing, confidence 75)
  - Why: KTD19 promises import 'validates every record and the header counts' and shows a readable error on failure. `parseBackup` has two distinct validation/error branches beyond the ones already tested (malformed JSON, wrong format tag, truncated counts, newer schema version): the `isValidTemplate`/`isValidSettings` check that throws 'The backup has a malformed template or settings' (lines 83-85), and the catch block that rewraps a `MigrationError` thrown while migrating an older-schema session or override into a user-facing `BackupError` (lines 98-101). Neither is exercised by any test in backup.test.ts, dataCommands.test.ts, or migrate.test.ts (migrate.test.ts only tests migrateSession's own MigrationError, never through parseBackup's wrapping). If the rewrap or the template/settings guard regresses, a user importing an old or slightly corrupted backup would see a raw, less-readable error (or a crash) instead of the promised message.
  - Suggested fix: Add two backup.test.ts cases: one that builds a valid backup, replaces `template` (or `settings`) with an object that fails isValidTemplate/isValidSettings, and asserts parseBackup throws BackupError(/malformed template or settings/); another that sets schemaVersion below current and includes a session shape known to fail migrateSession's validation (mirroring migrate.test.ts's `migrateSession({ id: 's1' }, SCHEMA_VERSION)` case), asserting parseBackup throws a BackupError carrying the migration error's message rather than an uncaught MigrationError.

- **P2** `src/domain/workout/actions.ts:358` — addRestTime's overtime-restart branch and the +30 s control are never triggered by any test (reviewer: testing, confidence 75)
  - Why: `addRestTime` branches on whether rest already finished: while running/paused it adds seconds to the existing `endsAt` (`addTime`), but once overtime (`rest.finishedAt` set) it discards that timer and starts a fresh one from `ctx.now` (`startTimer`) — a distinct, non-trivial behavior since overtime is a common real state (the user rested longer than planned). No test anywhere calls `addRestTime` in the `finishedAt`-set state: StrengthScreen.test.tsx's rest-timer test clicks '+15 s' once, before the timer expires, and never afterward; a project-wide grep for '+30 s' and for `addRestTime`/`endRest` in any *.test.ts(x) file returns zero matches. A regression that reuses the stale expired `endsAt` instead of restarting from now would show an already-negative or nonsensical countdown the next time a user extends rest after it hit zero, and nothing in the suite would catch it.
  - Suggested fix: Add an actions.test.ts case for addRestTime that starts rest, advances past its end so `rest.finishedAt` is set, then calls addRestTime(session, 15, ctx) and asserts the result clears finishedAt and sets a fresh endsAt of `ctx.now + 15000` (not the old endsAt + 15000); extend StrengthScreen.test.tsx's rest-timer test to also click '+30 s' at least once so the wiring from button to action is covered.

- **P2** `src/domain/workout/resync.ts:45` — resync's multi-step chaining within one call is never exercised (reviewer: testing, confidence 75)
  - Why: The docstring on `resync` states 'a long absence can stack several (get-ready → work → done)' and its guard-loop (line 24, `for (let guard = 0; guard < 32; guard++)`) exists specifically to resolve more than one expired timer in a single call — e.g. a phone lock during a warm-up step's 3-second get-ready countdown, long enough that the step's own duration has also elapsed by the time the app resyncs. Every resync test that touches get-ready ('turns an expired get-ready into a running step...') or step completion ('resolves a step that expired while closed once...') advances `now` far enough to trigger exactly one resolution, never both in the same call. The interaction between the get-ready branch's unconditional timer restart (lines 49-53) and the immediately following iteration re-checking that new timer for expiry is therefore unverified; a bug here would surface as a warm-up step silently skipping or double-completing after a phone lock during get-ready, which is a common real interruption.
  - Suggested fix: Add a resync.test.ts case that starts a warm-up step with getReadyCountdown true, then calls resync() once with `now` advanced past both GET_READY_MS and the step's full plannedSec (e.g. T0 + 3000 + step.plannedSec*1000 + 5000), asserting the step is marked completed, the index advances, and — because the elapsed time is not 'fresh' — the next step's timer is NOT auto-started, matching the 'never chains while stale, even if visible now' rule already covered for the single-expiry case.

- **P3** `src/features/home/HomeScreen.tsx:79` — Home shows current targets as 'Next workout after this one' (reviewer: correctness, confidence 75)
  - Why: While a workout is in progress, Home heads the list 'Next workout after this one'. The list is derived only from completed real sessions, so it actually shows the targets the active workout was built from (during a reopen, the previous session's targets). After a successful workout the real next targets differ, e.g. 5/5/6 rather than the 5/5/5 shown. Mid-workout the user reads today's targets under a heading that promises future ones.
  - Suggested fix: While a session exists, label the list for what it is, e.g. 'Current targets (update when you finish)', or hide it during an active workout.

- **P3** `src/features/home/HomeScreen.tsx:164` — Stale 'Finish & save' silently marks untapped sets skipped (reviewer: correctness, confidence 75)
  - Why: For a workout idle more than 4 hours, Home's 'Finish & save' marks every pending set as skipped and finishes without asking. It also finishes workouts where nothing was logged. KTD10 requires every exercise with pending sets to be resolved as done or skipped with nothing preselected, and a nothing-logged workout to offer Discard, precisely so a forgotten tap never silently fails an exercise. The usual reason a workout goes stale is forgetting to tap Finish, sometimes along with the last set. In that case this path records the exercise as failed and repeats it next time, and an accidental START turns into an empty workout in History. finishWithWhatsLogged also has no error handling, so when Finish is held on an unsaved write (SaveNotConfirmedError) the tap does nothing. Sending stale Finish through the existing FinishSheet restores the rule.
  - Suggested fix: Open FinishSheet from the stale card instead of finishing directly. Add a `stale?: boolean` prop to FinishSheet and pass it on as `finish(choices, { stale })`, render the sheet from ActiveWorkoutCard, and let its existing isLogged/Discard branch handle empty workouts. Surface errors in the UI instead of `void`-ing the promise.

- **P3** `src/features/summary/ExerciseResult.tsx:88` — Choose-resistance stepper keeps current reps instead of rung reset (reviewer: correctness, confidence 75)
  - Why: When a bodyweight exercise tops its ladder, the summary's resistance stepper saves the new load together with whatever reps the current target has. After 'Stay at BW' (BW 6/6/6), tapping + saves BW + 2.5 kg at 6/6/6: the top rung at a heavier load, not the 5/5/5 restart R12/R15 require and the engine itself applies (evaluate.ts:39-46). The reverse also goes wrong: stepping - from the suggested BW + 2.5 kg back to BW saves BW 5/5/5, restarting a ladder the user just finished, while 'Stay at BW' saves 6/6/6 for the same displayed load. The control shows only the load, so the reps change goes unnoticed until the next workout. Choosing the reps from the chosen load fixes both cases.
  - Suggested fix: In ChooseResistance, pick reps from the chosen load: `const repsFor = (kg: number) => (kg === log.planned.loadKg ? plannedReps : bottomRung(plannedReps.length, log.scheme.minReps))`, and call `save(next, repsFor(next))` in both stepper handlers (log.kind is already narrowed to 'reps' there).

- **P3** `src/services/dataCommands.ts:95` — Restored settings ignored until reload, then reverted by any toggle (reviewer: adversarial, confidence 75)
  - Why: Restoring a backup with newer settings writes them to IndexedDB, but the store keeps the settings it loaded at hydration. Settings still shows the old values, the ticker keeps the old get-ready flag, and the theme does not change. The next toggle calls updateSettings, which spreads the stale in-memory settings plus the patch and saves them with a fresh updatedAt, silently overwriting every restored value. Pushing the imported settings into the store after applyImport fixes both symptoms.
  - Suggested fix: After applyImport succeeds and plan.settings is present, call useWorkoutStore.getState().setSettings({ ...DEFAULT_SETTINGS, ...plan.settings }). For example, do it in DataSettings.confirmImport, or have applyImport return the applied settings for the caller to set.
